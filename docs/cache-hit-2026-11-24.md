# 上下文缓存命中率：实测结论与修复（2026-11-24）

## 一、DeepSeek 前缀缓存的实测行为（用本机 Key 直接调 API）

| 场景 | prompt tokens | 命中 tokens | 命中率 |
| --- | --- | --- | --- |
| 首次请求（无缓存） | 501 | 0 | 0% |
| 第二次请求，system+user+assistant 前缀完全一致 | 521 | 384 | **73.7%** |
| 前缀 58 tokens | 88 | 0 | 0% |
| 前缀 132 tokens | 132 | 0 | 0% |
| 前缀 221 tokens | 221 | 0 | 0% |
| 前缀 401 tokens | 401 | 256 | **64%** |

结论：
1. **前缀完全一致时缓存确实生效**（74%）。
2. **前缀太短时完全不缓存**：221 tokens 及以下命中 0，401 tokens 才命中 256。
   即「新会话前几轮显示 0%」是服务端行为，不是 App 的 bug。
3. `usage.prompt_tokens` **包含命中部分**（384 + 137 = 521），
   `prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens` 都给命中数。

## 二、App 侧原来的两个问题

### 1. 每轮都改 system → 前缀永远对不上（主因）

`_buildRequest` 把「人格 / 情绪 / 工作记忆召回」拼进 **system**，而这些内容每轮都变
（心情行、召回片段带日期）。system 是第一条消息，它一变，后面整条历史的前缀全部失效，
命中率只能靠运气。

**修复**：易变注入改挂到**最后一个 user 轮的开头**；system 只保留稳定内容
（基础提示词 + 排版约束 + 摘要 + 不带轮数的长期记忆提示）。历史链因此能整段命中。

### 2. 命中率公式把 DeepSeek 的数字算低了

旧公式：`命中 / (输入 + 命中)`。
DeepSeek 的 `prompt_tokens` **已含命中**，所以分母被算重了：
74% 的真实命中率会被显示成 `384 / (521 + 384) = 42%`。

**修复**：按供应商口径分分母——
- OpenAI / DeepSeek：分母 = `prompt_tokens`；
- Anthropic：分母 = `input + cache_read + cache_creation`（Anthropic 的 input 不含缓存）。
判别方式：Anthropic 会报 `cache_creation_input_tokens`，OpenAI 兼容接口没有。

同时补了 `prompt_cache_hit_tokens` 的兜底解析（有的版本不带 `prompt_tokens_details`）。

## 三、修复后模拟器实测

- 长会话（2952 tokens，导入包里的历史）：累计命中率从 29% → **48%**（含修复前的旧请求）
- 新会话前两轮：0%（149/207 tokens，低于服务端缓存门槛，符合上表）
- 单条请求 500 tokens 级别时预期 60–75%

## 四、还能进一步压成本的点（未做）

1. 摘要（≤600 字）放在 system，摘要更新会让整段前缀失效一次；可以改成「摘要作为
   最后一条 user 的消息前缀」，代价是摘要每轮重算会污染会话前缀一致性。
2. 历史里每轮 assistant 都带 `thinking` 块（当前只在 search 时回传 `reasoning_content`），
   如果以后全量回传，会显著增大前缀、也更容易命中——但成本也变高。
3. 新会话前 1–2 轮天然 0%，UI 可在命中率为 0 且 prompt < 256 tokens 时显示
   「前缀短，暂不参与缓存」而不是直接写 0%。
